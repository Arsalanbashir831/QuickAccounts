Implement a lightweight, scalable serial-number tracking layer on top of the existing QuickAccounts sales/returns/replacement architecture without redesigning the current quantity-based inventory system or adding purchase-time serial tracking. The goal is to support warranty/resolution verification by serial number, trace original and replacement units, and keep exact serial lookup fast even when one invoice contains 1,000+ serials. Add a new `erp.sold_item_serials` table that stores `id`, `company_id`, `item_id`, `sales_invoice_id`, `sales_invoice_line_id`, `serial_number`, `normalized_serial`, and timestamps; serials must be captured only when a sales invoice or replacement invoice is posted for items with `track_serials=true`, bulk inserted efficiently, validated so the number of serials matches the invoice-line quantity, and protected from accidental duplicate registration using an appropriate company/item/normalized-serial constraint while still allowing the same serial text to exist for another product where valid. Add `erp.sales_return_serials` to link returned serials to the existing `sales_returns` / `sales_return_lines`, and add `erp.replacement_serial_links` to link `sales_return_replacements.id` with the returned/original sold serial and the newly issued replacement sold serial, allowing chains such as `SN001 -> return -> replacement REP-001 -> SN900 -> later return -> REP-002 -> SN1500`. Preserve all existing invoice, return, credit, replacement, repair, custody, warehouse, costing, and accounting behavior; the serial layer is for identity, verification, and traceability only, while inventory quantities and GL remain handled by the current architecture. Implement a fast exact serial lookup API using PostgreSQL B-tree indexes, preferably `(company_id, normalized_serial)` plus supporting indexes for item/invoice/return relationships, normalize search input consistently, avoid JSON serial arrays and N+1 queries, support bulk validation/insertion for 1,000+ serials, paginate invoice serial listings instead of returning all serials by default, and expose lookup results that can resolve serial -> product -> invoice -> customer -> return history -> replacement ID -> replacement serial history. A returned serial must be verified as belonging to the correct source invoice line before it can be attached to a return, and replacement serials must be associated with the existing `sales_return_replacements` record and replacement invoice. Add database constraints, RLS/company isolation, idempotency/revision behavior consistent with the existing backend, migrations, serializers/API endpoints, selectors/services, audit/outbox events where appropriate, and focused tests covering bulk invoice serial creation, duplicate handling, exact indexed lookup, original-sale serial returns, replacement serial linking, multi-generation replacement chains, 1,000+ serial invoices, concurrent duplicate attempts, and rollback on posting failure.
